# VeloRead 总览

> 本文是 specs 的入口。产品定位、模块划分、格式支持矩阵、术语都在这里；
> 每个模块的详细契约见各自的 spec。

## 1. 定位

**VeloRead 是一款 macOS 桌面阅读器，目标是替代 Kindle 成为日常英文阅读的主力工具。**

三条主线，缺一不可：

1. **读得进去** —— 排版和翻页体验对得起长时间阅读
2. **读得更快** —— 自动阅读引导视线，训练打破默读习惯
3. **读完有沉淀** —— 划线和生词都能导出成纯文本，交给外部工具继续处理

### 两个参照物

| 参照 | 学什么 |
| --- | --- |
| **Apple Books** | 阅读视图与排版：风格主题、字体/字号/行距/页边距的调节方式、目录与书签的组织、极简自动隐藏的阅读界面 |
| **Kindle** | 沉淀与互通：`My Clippings.txt` 的摘抄格式、生词本（含例句与出处）的数据结构 |

**但有一条我们和它们都不一样**：Kindle 的摘抄和生词本导不出来，Apple Books 的笔记锁在 Apple 生态里。
**VeloRead 的数据必须能完整导出成纯文本**，这是产品的立身之本，不是可选项。

## 2. 产品原则

1. **本地优先**：默认全本地，不上传任何书籍或笔记。仅在用户显式开启的联网功能中发起请求。
2. **导出优先，绝不锁定**：任何用户产生的数据（划线、生词、进度）都必须有纯文本导出路径。
3. **能导入**：用户是从 Kindle 迁移过来的，历史数据要能带过来（见 [annotations](annotations.md)、[vocabulary](vocabulary.md)）。
4. **浏览器目标始终可跑**：平台能力走适配层，`bun run dev` 能用于日常迭代与线上 demo。
5. **开源为前提**：不引入需要闭源服务或付费依赖的方案。

## 4. 格式支持矩阵

支持三种格式，但**能力不对等**，这一点必须在产品上讲清楚，不能让用户以为 PDF 和 EPUB 一样好用：

| 能力 | EPUB | TXT | PDF |
| --- | :---: | :---: | :---: |
| 分页阅读 | ✅ | ✅ | ✅ |
| 进度记忆 | ✅ | ✅ | ✅ |
| **换字体 / 字号 / 行距** | ✅ | ✅ | ❌ 固定版面 |
| **视觉风格主题** | ✅ | ✅ | ⚠️ 仅背景色调 |
| 目录导航 | ✅ | ⚠️ 靠规则切分 | ✅ 若有书签 |
| **自动阅读 Pacer** | ✅ | ✅ | ⚠️ 依赖文本层 |
| 划线摘抄 | ✅ | ✅ | ⚠️ 依赖文本层 |
| 划词查询 | ✅ | ✅ | ⚠️ 依赖文本层 |

**根本原因**：EPUB 和 TXT 是可重排的（reflowable）文本，PDF 是固定版面。
排版类功能对 PDF 在物理上就不成立；扫描版 PDF 没有文本层，划线和 Pacer 都无从谈起。

**因此的工程结论**：EPUB 与 TXT **共用同一套渲染与标注引擎**（TXT 归一化成 HTML 后走同一条路），
PDF 是**独立的一条轨**，功能对等性天然打折。详见 [reading-formats.md](reading-formats.md)。

## 5. 术语

| 术语 | 含义 |
| --- | --- |
| **Locator** | 格式无关的位置标识。EPUB 用 CFI，TXT 用字符偏移，PDF 用页码+偏移。见 [reading-formats](reading-formats.md) |
| **CFI** | EPUB Canonical Fragment Identifier，EPUB 内部的精确位置锚点 |
| **注视块（fixation chunk）** | Pacer 一次高亮的阅读单位组；英文默认 3 词，CJK 默认 4 个字素 |
| **风格（Style）** | 一整套成品排版：配色 + 字体 + 字号 + 行距 + 版心，选中即整组套用 |
| **版心（measure）** | 正文每行的宽度，以字符数计（目标 45–75） |
| **摘抄（clipping）** | 与 Kindle `My Clippings.txt` 对齐的一条划线/笔记/书签记录 |
| **合集（collection）** | 用户自建的书架分组，一本书可同时属于多个。见 [library](library.md) |
| **打卡（check-in）** | 由有效阅读分钟数自动产生的每日达标记录，分四档。见 [reading-activity](reading-activity.md) |

## 6. 里程碑

按依赖顺序，不是承诺排期：

1. **阅读闭环**（✅ 已完成）：导入 EPUB → 渲染翻页 → 进度持久化 → 平台适配层
2. **像样的阅读器**（✅ 已完成）：排版与风格系统、字体设置、目录、位置信息、书签、滚动模式
3. **自动阅读与统计**（✅ 已完成）：Pacer 引擎、可信计时、趋势总览与每日打卡
4. **格式扩展**：TXT（与 EPUB 共用引擎），之后 PDF（独立轨）
5. **沉淀**（🚧 进行中）：划线笔记与书内列表已完成；摘抄导出与 Kindle 格式导入待做
6. **词汇**：词典入 SQLite、划词、生词本、导出

## 7. 候选功能（尚未纳入任何里程碑）

调研 Apple Books / Kindle / KOReader / Readwise 后，认为值得考虑但**还没决定做不做**的：

**高价值、与产品目标直接相关**
- **从 Kindle 迁移**：解析 `My Clippings.txt` 与 `vocab.db`，把历史摘抄和生词导入。
  用户正是从 Kindle 迁过来的，这是留住人的第一步。
- **按个人速度估算剩余时间**：「本章还剩 12 分钟」。Kindle 最被低估的小功能，
  而我们有 Pacer 的真实速度数据，能比 Kindle 估得准。
- **更深入的速度趋势**：按会话展示 Pacer 实际吞吐与理解训练变化。基础时长、字数、连续天数与打卡已实现。

**中等价值**
- 脚注/尾注就地弹出，不跳走
- 书库的阅读状态筛选（未读 / 在读 / 读完）；合集已实现，见 [library](library.md)
- 元数据编辑（修正错误的书名/作者/封面）
- 宽窗口下的多栏排版（Apple Books 有）
- 全库数据一键导出（备份）

**存疑，需要product判断**
- **朗读（TTS）**：macOS 系统语音质量不错，且与「训练阅读速度」有协同（听读同步能强行提速）。
  但会把产品往「听书」方向拉，可能偏离主线。
- **划线的间隔重复复习**（Readwise 那套）：与「导出优先」的定位冲突 ——
  我们的立场是把数据交出去，而不是自己做一个复习系统。倾向不做。
- **Word Wise 式生词就地注解**：旧实现做过（硬编码 150 词），效果取决于词频表质量。
- **跨设备同步**：优先走 iCloud Drive / 用户自选目录，而不是自建服务。

**明确不做**
- 书城 / 内购 / DRM 书籍
- 社交功能（共享划线、热门标注）
- 云端账号体系

## 8. 非功能要求

- **性能**：打开 >20 MB 书籍无明显卡顿；划词查询响应 < 50 ms
- **词典**：本地词典以 SQLite 存储并建索引，不整包载入内存
- **数据安全**：书籍与笔记存在用户可见目录；卸载应用不丢数据；提供一键导出全部数据
- **可访问性**：所有阅读操作可用键盘完成；释义提示不依赖 hover；尊重 `prefers-reduced-motion`
- **应用体积**：安装包目标 < 30 MB（不含词典数据）
